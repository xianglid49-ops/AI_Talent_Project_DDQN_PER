# AI-Enabled Dynamic Talent–Project Matching — Reproducibility Code

This repository contains a flat, reviewer-oriented implementation of the computational pipeline described in **“An AI-Enabled Platform for Dynamic Alignment of Individual Capabilities and Project Needs.”**

The implementation is intentionally aligned with the revised methodological position:

- **Adaptive RL algorithm:** Double Deep Q-Network (**DDQN**) with **Prioritized Experience Replay (PER)**.
- **No PPO, MAML, or formal meta-learning optimizer is implemented.**
- Dataset-native variables are kept separate from simulation-generated variables.
- Dynamic workforce behavior is treated as a **controlled semi-synthetic simulation**, not as observed longitudinal workforce data.
- Matching labels are generated by an explicit, configurable heuristic and are interpreted as agreement with that compatibility rule rather than real hiring/project-success ground truth.
- The primary evaluation protocol is **5-fold stratified cross-validation**. In each fold, the 80% development partition is further divided so that **15% of the development partition** is used for validation; the untouched 20% fold is the test partition.
- Every fold is repeated using multiple random seeds.
- Rule-based, TF-IDF, Transformer-only, GNN-only, and the complete GNN–Transformer–DDQN-PER pipeline are evaluated using the same held-out folds.
- SHAP is applied to the **final prediction head using fixed learned latent representations**. It is not presented as an explanation of internal graph message passing.

## Dataset

The supported public dataset is:

**Industry-Education Skills Matching Dataset**  
Kaggle dataset slug: `programmer3/industry-education-skills-matching-dataset`

The code supports either:

1. a local CSV supplied with `--data`, or
2. automatic acquisition with `kagglehub` using `--download`.

The dataset is static. Candidate identities, project identities, project transitions, availability, collaboration, behavioral compatibility, experience accumulation, learning velocity, and feedback/reward signals are generated only inside the simulation code and are marked as simulated in the generated provenance file.

```bash
source .venv/bin/activate

```

## Reproduce with a local CSV

```bash
python reproduce.py --data /path/to/dataset.csv --config config.yaml
```

## Reproduce by downloading the Kaggle dataset

```bash
python reproduce.py --download --config config.yaml
```

`kagglehub` may require the user's Kaggle authentication depending on the execution environment.

## Fast smoke test

```bash
python reproduce.py --data /path/to/dataset.csv --config config.yaml --smoke
```

Smoke mode reduces epochs, seeds, and fold count only to verify that the complete pipeline executes. It must not be used to report manuscript results.

## Main generated artifacts

A timestamped output directory is created automatically and contains:

- `provenance.json` — dataset source, discovered columns, dataset-derived vs simulated variables.
- `label_definition.json` — exact heuristic compatibility formula and threshold.
- `split_manifest.csv` — fold, seed, row index, and train/validation/test membership.
- `fold_metrics.csv` — fold- and seed-level metrics for every method.
- `summary_metrics.csv` — mean, standard deviation, and 95% CI.
- `paired_tests.csv` — paired statistical comparisons between the proposed method and baselines.
- `topk_metrics.csv` — ranking-oriented Top-k hit rates.
- `predictions.csv` — held-out scores and predictions.
- `shap_feature_importance.csv` — SHAP feature importance for the final prediction head.
- `run_config.json` — resolved configuration used for the run.
- trained model checkpoints for the best validation run of each fold/seed.

## Label-generation protocol

The evaluation labels are deliberately explicit. The default heuristic is:

\[
C(i,j)=w_s S_{skill}(i,j)+w_r S_{role}(i,j)+w_c S_{course}(i,j)+w_d S_{demand}(i,j)
\]

and

\[
y_{ij}=\mathbb{1}[C(i,j)\ge \tau].
\]

The default weights and threshold are defined in `config.yaml`.

Important safeguards:

- The label generator uses **dataset-derived features only**.
- Simulated availability, behavior, collaboration, learning velocity, and synthetic project outcomes are excluded from ground-truth construction.
- The proposed model may use simulated dynamic features during adaptive-policy training, but held-out evaluation is always reported against the explicit heuristic label.
- The resulting metrics therefore quantify agreement with the declared compatibility criterion, not independently observed hiring success.

## DDQN-PER implementation

The adaptive module contains:

- online Q-network and target Q-network,
- Double-DQN target selection/evaluation,
- proportional prioritized replay,
- importance-sampling correction,
- epsilon-greedy exploration,
- soft target updates,
- gradient clipping,
- deterministic seed handling.

The RL state contains the fixed GNN–Transformer pair representation plus explicitly simulated operational signals. The action is binary:

- `0`: do not assign
- `1`: assign

The Q-value advantage is combined with the supervised matching probability only in the **complete proposed model**. Baselines never receive RL-derived information.

## GNN–Transformer matcher

For every candidate–project pair, a compact heterogeneous graph is constructed with:

- one candidate node,
- one project node,
- one node per discovered skill dimension.

Candidate–skill and project–skill edges are weighted by the corresponding proficiency/requirement values. A graph-attention layer performs local relational aggregation. A Transformer encoder then models global interactions across the graph tokens. The final representation is concatenated with interpretable pair-level features before prediction.

This implementation avoids introducing unrelated supply-chain, route-planning, or navigation concepts.

## Explainability

SHAP is computed only on the final prediction head. The graph/Transformer encoder is first used to generate fixed latent pair representations. SHAP then explains the prediction head with:

- latent graph–Transformer dimensions,
- skill overlap,
- project complexity,
- experience relevance,
- learning velocity,
- cultural/behavioral fit,
- availability,
- collaboration compatibility.

The default background set contains up to 500 validation samples.

## Reproducibility and reporting rules

Do not copy claimed performance values into the manuscript before running this code. The repository intentionally recomputes all values from the dataset and resolved configuration.

If generated metrics differ from the current manuscript, the manuscript should be updated to the reproducible outputs. This is preferable to modifying code to force a target number.

## Archival step before final acceptance

After verification, create a tagged release from the exact commit used for the manuscript and archive that release in the journal-accepted permanent software repository. The manuscript's Code Availability section should point to the archived version corresponding to the reported experiments.
